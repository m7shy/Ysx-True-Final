## The single highest-leverage fix

**There is no Express error middleware and no `unhandledRejection` handler anywhere in
the server.** [V — grep across `server/src` returns zero hits]

Express 4 does not route a rejected `async` handler promise to an error handler. The client
gets no response and the connection hangs; under Node's default `--unhandled-rejections=throw`
the process then aborts, killing the API, campaign worker, follow-up scheduler and reply poller
together.

Three of the four reviewers hit this independently from different directions. It is what turns
several otherwise-ordinary bugs into process kills:
- `P2002` on concurrent signup (unit 1)
- a `WEB_ORIGIN` without a scheme, thrown from inside a `catch` block (unit 1)
- `amountCents: 3e9` — passes Zod (`.int().positive()`, no max), overflows a Postgres `integer` (unit 4)
- any Prisma blip in `unibox/routes.ts` or `scraper/routes.ts` (unit 3)

Fix: a terminal 4-arg error middleware after the static handlers, plus
`import 'express-async-errors'` at the top of `index.ts` (or Express 5), plus
`process.on('unhandledRejection')` as a backstop.

## HIGH — verified

### 1. Any second campaign to an existing audience is a silent no-op [V]
`server/src/campaigns/worker.ts:350` skips any recipient whose lead is not `NEW`. The first send
sets `CONTACTED` (`worker.ts:132`), and `upsertRecipientsAsLeads` never resets it. So campaign #2
to the same list marks every row `SKIPPED`, sends nothing, and reports `COMPLETED` at 100%.
`INTERESTED`, `CALL_BOOKED` and `TRIAL` leads are likewise permanently unmailable.
Fix: gate on the real blockers (`DNC`, `LOST`, `isBounced`, optionally `REPLIED`), not on `!== NEW`.

### 2. Corporate link scanners silently unsubscribe leads [V]
`server/src/campaigns/trackingRoutes.ts:160-172` — `GET /t/u/:token` **performs** the unsubscribe
and then renders the page. The comment at `:125` calls it a confirmation page; it is not.
The URL sits in the visible body of every email (`trackedHtml.ts:59,69`). Defender Safe Links,
Proofpoint et al. GET every URL in an inbound message — each scan sets the lead to `DNC`, cancels
its follow-ups and skips its pending recipients. Also outside the rate limiter (`index.ts:80`).
Fix: GET renders a POST form; mutate only on POST. `POST /t/u/:token` (RFC 8058) is already correct.

### 3. Portal magic-link is an unauthenticated mail relay on the tenant's metered quota [V]
`portalAuthLimiter` sets `skipSuccessfulRequests: true` (`server/src/index.ts:140`) and
`POST /magic-link` **always** returns `res.json({ ok: true })` (`portal/auth.ts:119`). Every request
counts as a success, so the 10-per-15-min budget is never decremented. Only the global 120/min
remains. Each request calls `sendPortalEmail` → `sendFromMailbox` → `assertUnderEmailLimit` +
`recordEmailSent` — the *same* metered counter the CRM's campaign sends use. An unauthenticated
attacker with one known client email can floodh that inbox from the agency's own mailbox, burn the
tenant's paid quota, and once exhausted every CRM campaign and follow-up send starts throwing
`LimitExceededError`. If the OAuth mailbox errors, `mailer.ts:63,73` falls through to the SMTP
fallback, which skips the quota check entirely.
Fix: dedicated limiter without `skipSuccessfulRequests`, keyed on `ip + normalized email`;
suppress a second send when an unexpired unused token exists; move the send off the request path.

### 4. Portal email enumeration via response timing [V]
`portal/auth.ts:105-119` awaits a full SMTP round-trip before responding when the address exists,
and returns after one indexed lookup when it doesn't — hundreds of ms vs ~5ms. The "no account
enumeration" comment at `:98` is false in practice; the existing test only asserts identical
*bodies*. Fix: respond first, send detached.

### 5. Concurrent OAuth refresh permanently deactivates a healthy mailbox [V]
`server/src/creds/mailboxStore.ts:88-145` is an unguarded read→refresh→write. Six call sites hit it
with independently-loaded snapshots (campaign worker, reply poller, `replyCheck`, every `/api/mail/*`).
Both decrypt the same rotating refresh token; AAD invalidates the first on use, the loser gets
`invalid_grant`, which `:117` treats as terminal and writes `isActive: false`. Ordinary concurrent
use disables the mailbox and forces a full re-consent. Fix: single-flight per mailbox id, plus don't
treat the first `invalid_grant` as terminal.

### 6. Scraper leaks YouTube session cookies across tenants [V]
`server/src/scraper/cookieService.ts:145` materializes the calling tenant's decrypted cookies into
one global directory with no tenant component, after deleting every `*.txt` already there. With
`MAX_CONCURRENT_CHILDREN=4`, concurrent runs are the designed case: tenant B's start deletes A's
cookies mid-run, and A's still-running child authenticates to YouTube as B. The `rows.length === 0`
early return at `:143` means a tenant with no cookies inherits whoever ran last.
Fix: per-run directory; drop the early return.

### 7. Token revocation does not exist [V]
`User.tokenVersion` is read in `jwt.ts`, `tenantGate.ts` and `routes.ts` and **written nowhere**
(grep confirms every hit is a read or a claim copy). There is no logout, no password-change and no
reset route. `ClientUser.tokenVersion` is identical (unit 4, M4) — and `Client.status = ARCHIVED`
is never consulted by any portal query, so archiving a client does not revoke their access either.
With a 30-day refresh TTL, a stolen token cannot be revoked by any available means.
Fix: `logout-all` + password-change that increment `tokenVersion`; check `Client.status` in
`requireClientAuth`; shorten the client refresh TTL.

## Not broken — worth knowing

- **No IDOR in the portal.** All 10 routes filter by `clientId` at the query level, including nested
  resources (`revisions/:id/approve` re-filters by `projectId`). This was the biggest risk in the new
  code and it holds.
- **Credential crypto is sound**: AES-256-GCM, fresh 12-byte random nonce per call, tag verified,
  key length enforced. The gap is key *rotation*, not the cipher.
- **CRM ↔ portal audience separation is complete in both directions** (`assertNoAudience` +
  `audience: CLIENT_AUD`), including `typ` checks.
- **Mail header injection is not possible** — nodemailer strips CRLF from header values.
- **OAuth callback CSRF is properly closed** — signed `state`, userId derived from the verified claim.
- **Mount ordering is correct** — webhook before `express.json`, import before `/api/leads`,
  portal auth before the gated router, all static/catch-all after every API router.
- **Framer Motion `display:none` bug is NOT present in the portal** (7 usages, all correct) and the
  Vite-root bug is fixed — both previously shipped bugs, both genuinely closed. *(unit 5, unverified)*
